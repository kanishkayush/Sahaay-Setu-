# Internationalisation

Six languages ship: **English, हिन्दी, मराठी, বাংলা, தமிழ், తెలుగు**.

```

```

All six are now complete. `en` remains the fallback for every key, so the mechanism still holds
if a key is added ahead of its translations (ADR-006).

**mr, bn, ta and te are AI-translated and not yet native-reviewed.** Each carries
`_meta.reviewStatus: "ai-translated-pending-native-review"`. These are financial terms in front
of people deciding whether to take on debt — get a native speaker over them before any public
deployment, starting from [`TRANSLATION_GLOSSARY.md`](TRANSLATION_GLOSSARY.md). See ADR-015.

The check **fails** only on keys present in a locale but absent from `en.json` — almost always
a typo or a leftover from a rename.

## How language is chosen

1. A stored choice from a previous session (AsyncStorage), else
2. the device language if we support it, else
3. English.

Language selection is the **first screen anyone sees**, before any content. Each option is
written in its own script — मराठी, not "Marathi" — because a user who cannot read English must
still be able to find their language. Selecting one switches the UI immediately.

It can be changed any time from the Profile tab.

## Two kinds of translatable text

Do not confuse them.

**UI copy** — buttons, labels, errors. Lives in `src/i18n/locales/*.json`, read with `t()`:

```tsx
const { t } = useTranslation();
<Text>{t('schemes.title')}</Text>;
```

**Backend content** — scheme names, eligibility labels, document lists. Arrives as a
`LocalizedText` map because the catalogue is data, not UI copy:

```tsx
import { pickLocalized } from '@/i18n/localized';
pickLocalized(scheme.name, language, scheme.code); // applies the en fallback
```

## Rules

- **No user-visible string is ever hardcoded.** Add it to `en.json` first.
- **Placeholders are code.** `{{count}}`, `{{rate}}`, `{{months}}` must survive translation
  intact. Translate around them.
- **Endonyms are never translated.** `SUPPORTED_LANGUAGES[].endonym` is the language's name in
  its own script, always.
- **Use `Text` from `@/components/ui`.** It carries the line heights Devanagari, Bengali, Tamil
  and Telugu need — Latin-tuned leading clips them.
- **Check overflow after adding a language.** Tab-bar labels and buttons are where it shows up
  first.

## Language for speech, not just text

Voice adds a second sense of "language": which voice the device speaks and listens in. That
mapping lives in [`src/features/voice/speechLocales.ts`](../src/features/voice/speechLocales.ts):

| App language | Speech tag |
| ------------ | ---------- |
| `en`         | `en-IN`    |
| `hi`         | `hi-IN`    |
| `mr`         | `mr-IN`    |
| `bn`         | `bn-IN`    |
| `ta`         | `ta-IN`    |
| `te`         | `te-IN`    |

**All six are the Indian variants deliberately, `en` included.** A bare `en` gets a US voice
that mispronounces every rupee figure and place name in the app — "lakh" and
"Tiruchirappalli" are the obvious ones — and the content is Indian regardless of which
language the interface is in.

Never build the tag by string concatenation. `` `${language}-IN` `` happens to work for these
six and silently produces nonsense for the seventh; use `speechLocaleFor()`.

### Not every device has every voice

The table above is what we _ask_ for. What the device can actually do is another matter, and
the failure is silent: asking a platform to speak a language it has no voice for reports
success while substituting a default, so Marathi text gets read with English phonetics and
nothing errors.

Measured on macOS, 2026-09-08 — `en-IN` (Rishi), `hi-IN` (Lekha), `bn-IN` (Piya), `ta-IN`
(Vani) and `te-IN` (Geeta) are installed; **`mr-IN` has none at all.** The voice set differs
per platform, so `canSpeak()` asks at runtime and the screens hide their read-aloud controls
rather than produce confident gibberish.

**Speech-to-text coverage is not knowable from code.** The Web Speech API exposes no list of
supported recognition languages. Chrome delegates to Google's engine, which documents all six
Indian locales; Safari uses Apple's, with different coverage. Someone has to speak each of the
six into a real device — that is tracked in `context/state.json → openQuestions`.

Both speech directions go through this: `startListening()` sets `recognition.lang`, and
`speak()` passes it to expo-speech. Adding a language means adding its row here too.

## Adding a language

Roughly fifteen minutes. Full steps in `.agents/skills/add-a-language/SKILL.md`:

1. `src/i18n/locales/<code>.json`
2. Add the code to `LanguageCodeSchema` in `src/api/contracts/common.ts`
3. Import it and register it in `resources` + `SUPPORTED_LANGUAGES` in `src/i18n/index.ts`
4. Add its display name to the `language` block of every other locale
5. Add its BCP-47 row to `SPEECH_LOCALE` in `src/features/voice/speechLocales.ts`
6. `npm run i18n:check && npm run verify`

## The AI speaks the same language

The chosen language is sent as `responseLanguage` on every assistant request and `language` on
every recommendation request, so answers come back in the language the user is reading. A user
may type Hindi while the UI is Tamil — the answer follows the UI.
